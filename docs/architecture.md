# Byeori v0.1 contract

This is the B01 implementation contract, not a claim that Core, Studio or hooks are implemented. `src/contracts/index.ts` is the common TypeScript surface for Core, CLI, HTTP Studio and host adapters. Core owns parsing, validation, lifecycle derivation, all managed writes and gate decisions. Neither an adapter nor a UI may reconstruct approval independently. One local user and one active change per configured workspace are supported.

## Durable files and cache

Paths below are relative to the initialized workspace. Existing files are preserved by init; imported documents begin as drafts. No product approval comes from development bootstrap or `.delivery/`.

```text
planning/config.yaml                              project identity and empty genesis
planning/workflow.yaml                            interview/resume context
planning/source/**.yaml                           currently applied planning
planning/changes/<change_id>/change.yaml           mutable request/metadata, no status flag
planning/changes/<change_id>/draft/**.yaml         lossless mutable draft
planning/changes/<change_id>/draft-manifest.yaml   draft IDs, paths and delete/move intent
planning/changes/<change_id>/rounds/<round>/manifest.yaml
planning/changes/<change_id>/rounds/<round>/before/**.yaml
planning/changes/<change_id>/rounds/<round>/after/**.yaml
planning/changes/<change_id>/rounds/<round>/feedback-draft.yaml
planning/changes/<change_id>/responses/<response_id>.yaml
planning/changes/<change_id>/cancelled.yaml
planning/changes/<change_id>/apply-transaction.yaml
planning/changes/<change_id>/applied.yaml
planning/changes/<change_id>/implementation/<implementation_id>.yaml
planning/reviews/submissions/<submission_id>.yaml  durable global idempotency receipts
planning/hosts/<host>.yaml                         capability observations/human advisory choice
planning/.runtime/write-lock/owner.yaml            surviving exclusive writer ownership
planning/.runtime/write-lock/recovery-claim/owner.yaml
.byeori/runtime/                                  disposable staging only
.byeori/index.sqlite                              disposable search index
```

The draft manifest expresses deletion/move even when no draft file exists. It does not add a second status database. Files describing immutable rounds, submissions, cancellation and applied results are create-only; overwriting them is a conflict. Product records are Git-trackable YAML. History is a projection of these records, not another event store or manual changelog. Init preserves existing ignore content and adds `/.byeori/` and `/planning/.runtime/` management rules. The ignored `planning/.runtime/` ownership anchor is non-disposable while any managed operation is live, incomplete or uncertain; it is not an approval/history store. `/.byeori/` can be deleted without losing ownership, approval, feedback, history, workflow or apply recovery.

`Hash`, `RecordId`, paths and timestamps in TypeScript are wire strings, not validated brands. Every disk, CLI, HTTP, hook and imported reference boundary must validate them. Types alone do not establish trust.

## Documents and validation

The eight native discriminated document types match the supplied planning JSON Schema without weakening required fields. They retain full PRD purpose/goals/scope/constraints; actor responsibilities and explicit permissions; scenario actors/preconditions/stable steps/outcomes; feature actors/rules/AC; IA nodes; screen components/actions/states; entity fields/key/constraints; and architecture components/connections/decisions. Common aliases, relations and open questions remain available in every native document. Nonfunctional requirements use the appropriate existing fields. No generic description field replaces a document body.

The ninth kind is standard OpenAPI 3.1.1, stored unchanged, with `info.x-byeori-id`. Its adapter returns a read-only projection plus the entire standard document for structured operations/request/response/schema/extension views. It derives operation relations from `x-byeori-features`; operationId must be present and unique for operations that can be reviewed. OpenAPI is not wrapped into the native planning schema. The full OpenAPI validator/schema is to be vendored and pinned during B03; B01 does not claim a minimal interface validates the standard. Remote `$ref`, scheme URLs and references outside the project are rejected without fetching. Local references are resolved only inside validated planning documents, including escaped JSON Pointer segments, with bounded recursion. No implicit network validator.

Parsing uses only the JSON-compatible subset of YAML 1.2. Reject duplicate keys, custom tags, anchors/aliases/merge, multiple documents, non-string keys, nonfinite numbers and unsafe numeric integers. B03 initial limits: 1 MiB raw per document, depth 64 and 100,000 parsed nodes, applied before/schema-independent of semantic checks. Larger exact integers are strings. All meaning is in fields; comments are preserved as raw history but are not requirements. Invalid/incomplete drafts retain exactly the submitted raw text and diagnostics. A failed parse is never silently coerced into an approved object.

Validation order: parser profile → local JSON Schema → globally unique object IDs and locally unique stable element IDs → typed reference/relationship validation on the complete projected source, including deletions → readiness → OpenAPI → round/source integrity. Reference checks cover relation targets, scenario/feature actor IDs, scenario step actors, IA screen IDs and local parent IDs, entity primary-key field IDs, architecture connection endpoints, and OpenAPI feature IDs/local references. Inverse relations are computed. Generic relatedness cycles are valid; only explicit `depends_on` cycles are rejected by policy. IA parent cycles are structurally invalid. Actor hierarchy confers no permission. A feature does not require a UI/screen relation. Screen action text is content, not executable code.

Schema validity is distinct from business/readiness review. Structural lint cannot claim semantic adequacy. Blocking projected questions must be resolved for the requested implementation stage before implementation authorization. A question/note never automatically becomes a requirement. Historical snapshots validate under their recorded versions and are readable even after the referenced current objects are deleted.

## Identity, paths and hashes

Core issues UUID/ULID identifiers for project/change/submission/comment/response/transaction/implementation records. A record path segment must match `^[A-Za-z0-9][A-Za-z0-9_-]{0,127}$`; native object IDs retain the seed schema's uppercase ID format. Display names and document IDs never directly determine record paths. Round is a bounded positive safe integer. Hashes are lowercase 64-character SHA-256; timestamps are UTC ISO 8601.

Canonical workspace identity contains the real absolute root and, when Git exists, the real common directory, per-worktree Git directory and symbolic branch ref (or detached HEAD hash). Fingerprint = SHA-256 of this canonical identity. Submission/prepare/apply recompute it rather than trusting a client field. Moving root, switching branch, changing worktree or crossing projects makes the review stale. Same-branch commits are not the source-integrity test. Gitless roots are supported with `git: null`. Init never silently rebinds an existing approved project to a new workspace. A changed binding requires a fresh review, not a cached approval transfer.

Paths use workspace-relative POSIX segments; source paths and snapshot paths have separately checked allowed roots. Reject absolute paths, drive/UNC paths, empty/dot/dot-dot segments, backslashes, NUL/control bytes and encoded traversal/separators at HTTP decoding boundaries. Do not recursively decode paths. Check canonical containment and reject symlinks in every existing ancestor/final entry, including managed directories and local OpenAPI references. Recheck at write time, not only on request admission. Reject duplicates/collisions in paths and IDs, including case-fold collisions on supported macOS filesystems. Scope cannot authorize planning records, cache, Git internals or traversal. User strings are data, never shell/SQL/HTML source.

Canonicalization `json-sorted-v1`: parse with the same bounded profile, recursively sort string keys by JavaScript ordinal comparison, preserve arrays and all string content, then serialize using JSON.stringify (negative zero becomes zero; no whitespace). Hash UTF-8 bytes with SHA-256. YAML formatting/comments alone do not invalidate semantic approval; raw bytes use a separate `raw_hash` and diff. Full source manifest sorts entries by path, then ID and includes project ID, schema/policy/canonicalization versions, path, ID, kind and content hash. Path moves/additions/deletions consequently change the source manifest even if object content is unchanged.

`config.yaml` freezes the project ID and an empty source manifest/genesis hash. A nonempty existing source with no verifiable chain is drift, never an imported approval. For every applied record, rederive the referenced round, snapshots, accepted durable submission and their hashes, require its base hash to equal the previous result, then advance to the next result from genesis. The frozen `base_applied_change_id` explicitly names the previous applied record (null at genesis), so implementation-only/no-op applies remain ordered even when base/result hashes are equal. Reject missing links, multiple successors of the same record, cycles, inconsistent versions and unverifiable snapshots. Finally compare the entire live source manifest with the resulting chain head. No mutable `approved` field, index entry, chat, file location or Git commit confers approval. Hashes detect consistency, not an attacker who rewrites all records with the same OS privileges; this is not a signed tamper-proof ledger.

Policy/schema/canonicalization versions are exact bundled versions. Unknown versions fail closed for current apply/gate; supported historical versions remain locally readable. v0.1 does not silently migrate old approvals when versions change.

## Freeze, review and durable human judgment

Change metadata stores type, request, reason, affected object IDs, related planning IDs, explicit implementation path allowlist and validation plan. Empty code scope represents planning-only work. `implementation_only` has no document delta but must have a nonempty reason, related approved planning IDs, nonempty allowlist and validation plan, and the required `scope:implementation` item. Any offered implementation scope is visible as a review item, also for a spec change. Scope entries are exact files or boundary-delimited directory subtrees, no glob or implicit `*` workspace access; newly needed code paths require a fresh review.

Prepare validates the whole base+proposed source under the lock and writes a new immutable round. Freeze raw before/after documents, full base/target manifests, metadata/reason/scope, workspace identity, schema/policy/canonicalization versions, all item definitions and explicit deltas. Snapshot-tree hash is the canonical sorted list of snapshot relative paths and raw hashes. Manifest hash covers all `ReviewManifest` fields; its own hash and preparation timestamp are outside the hashed manifest. `metadata_hash` hashes metadata and `scope_hash` hashes the exact implementation scope. UI reads this manifest and snapshots only. Deletion and path moves are explicit; all permission/scope changes are reviewable. A new change version never overwrites an existing round.

Lifecycle is derived: change only → draft; latest frozen round without an accepted final judgment → in_review; accepted pending/request_changes/blocking feedback → needs_revision; valid complete final confirmation → approved; verified durable applied record → applied; valid cancellation of an unapplied change → cancelled. Each round has at most one accepted final submission, including pending/request_changes judgments. A different judgment requires a new frozen round; no newest/any-approving-receipt selection is allowed. Invalid/stale records or multiple accepted receipts for one round produce diagnostics, not an optimistic approved state. Only draft/in_review/needs_revision/approved are active; creation under lock fails if one already exists. New rounds may show old judgments for reference but do not inherit decisions or final confirmation. An applied change cannot be cancelled.

Autosave writes `feedback-draft.yaml` atomically and durably under the shared lock, comparing `expected_version` against the current payload hash (`null` only for first create). On mismatch return CONFLICT/HTTP 409 and preserve the browser's unsaved input copy. Reject every autosave for a finalized round, even if its version matches; it cannot reopen/alter final decisions or authorization. Only server confirmation after durable save produces “saved”; save failure leaves input available. Autosave version hashes binding+feedback, excluding version/saved_at fields. Autosave, even with every item approve, is not a submission or approval.

Only the authenticated Studio explicit-submit route invokes `HumanReviewApi.submitReview`, after the user sees item decisions, deletions, purpose and implementation scope and explicitly confirms. No agent CLI/hook can submit/approve, and no production test helper exists. The receipt stores the full validated submission, its payload hash, submission time and provenance. Provenance is a record of the supported route, not cryptographic identity proof. Bootstrap and “review complete” chat cannot call this route on the user's behalf.

Submission binds project/workspace/change/round/manifest and requires `expected_feedback_version` matching the current durable saved draft. Its binding+feedback must equal that saved body exactly; the submit route cannot silently replace stale/unsaved item decisions, comments or implementation permission. Core requires explicit final confirmation, the current frozen round, unchanged base, intact snapshots, current versions, exact item coverage once each, unique valid comments and targets inside that round, and current metadata hash. Targets use stable object/element/field or OpenAPI operationId/escaped pointer, never bare line numbers or array-index identity; `scope:implementation` is a synthetic scope target. Pointer-only targets may address stable map fields; array children require element/operation identity. IDs outside the round or nonexistent fields/elements are rejected.

Under the surviving shared lock, submit first checks the globally unique submission ID's durable receipt: same ID+canonical payload returns the original receipt before current-round, saved-draft or apply freshness checks, even after a new round/apply/restart; same ID+different payload returns CONFLICT. For an unseen ID, reject an already finalized round (CONFLICT/409), then perform saved-body/version and all fresh-binding checks, and durably create its unique accepted receipt before returning. The receipt itself is finalization evidence; no second flag must be written to make it authoritative. Concurrent distinct IDs therefore accept exactly one judgment. Approval/apply reference that unique accepted submission. Lost responses replay the original result without reopening the round.

Approval requires final confirmation, every required item approved, no pending required item, no request_changes and no blocking comments, stage readiness, latest base/manifest and matching policy. Every manifest item is required in v0.1. Document approval and implementation permission are separate: `allowed: false` requires null scope hash; `allowed: true` requires the exact frozen scope hash, nonempty scope, resolved implementation-blocking questions and approved scope item. Neither field alone opens the gate.

Any reason/request/type/affected-object/scope/validation-plan change increments the change version and invalidates the old approval (A16), even if documents are identical. Draft content changes belong to a new round. Apply compares current metadata semantically to the frozen metadata as an invalidation check, but uses no mutable metadata/content to construct its writes or scope (A17). YAML formatting-only metadata/source edits with identical canonical content do not invalidate semantic approval. Editing frozen raw snapshots invalidates snapshot integrity.

Responses bind submission and round and record comment_id, result, changed paths and rationale. `addressed_in_draft` does not resolve or approve a human comment. Persist response/draft progress under the same lock with expected change version and durable response ID/payload idempotency; retries cannot silently repeat a change. Resume reads submissions, responses and workflow feedback progress before modifying drafts. Corrections are at most two ordinary attempts plus one cause-analysis/escalation attempt per product workflow; new human decisions stop automation. This is not a development-team quality limit.

## Apply and recovery

All managed mutations, including init/config writes, drafts, feedback, responses, workflow, prepare, human submissions, source apply, recovery and index rebuild, share one Core workspace lock. Create only missing lock ancestor directories idempotently during init bootstrap; then acquire `planning/.runtime/write-lock/` by exclusive atomic directory creation and durably create its `owner.yaml` before any managed content writes. The original owner has matching random anchor/owner nonces plus OS-observed PID, process-start identity, host boot identity, operation and acquisition time. B04 must observe process-start identity on supported macOS/Linux; PID alone or an unverified caller timestamp is insufficient. A partial/malformed owner record or unknown liveness denies mutation; no lease expiry or automatic live/uncertain takeover. Cache deletion never removes this anchor. Reads detect unfinished transactions and fail/wait boundedly rather than read a partial source tree.

Recovery of a dead original owner is serialized by exclusive atomic creation of `write-lock/recovery-claim/`, with its own durable owner/nonce record. Before claiming and again after publishing the claim, verify the unchanged original anchor nonce and prove the original process identity is dead (not merely a different PID lookup). Competing recover calls encountering any existing claim deny; they cannot replace/remove it. Missing/malformed/partial claims fail closed. If a claimed recovery itself dies, automatic reclamation is intentionally blocked pending explicit operator recovery of the exact anchor/claim after all recorded owners are proven dead; it never guesses which claimant may proceed. This bounded failure needs recovery guidance, not a second writer.

The apply journal persists its current `WriteOwnership` including anchor and active-owner nonces. A successful dead-owner claimant durably updates journal ownership before resuming source writes. Original owners recognize a claim as ownership loss. Every owner verifies the surviving anchor, applicable claim and journal nonces before each further managed write/rename/delete and after asynchronous boundaries; losing/missing/uncertain ownership stops further writes. Only the currently verified owner releases the lock after its operation is safely completed. No invocation removes/replaces another live owner's anchor, and recovery never starts on journal contents alone. If ownership evidence is missing, an unfinished journal retains its recorded owner's identity; resume remains denied until that owner is proven dead and exclusive ownership is re-established. No persistent daemon or general lease/event store is introduced.

Apply runs: lock → inspect all durable journals → rederive approval/source chain and recompute workspace → compare full live base, frozen predecessor record ID, policy and metadata → validate the complete frozen projected after, including deletions → durably create apply transaction → stage and atomically replace each file where available → verify final full tree → durably create applied record → mark journal completed → refresh disposable index → unlock. Records/files require file flush and directory durability where supported; platform limits must be reported/tested, not called a multi-file atomic transaction. A successful applied record precedes cache refresh, so cache failure does not undo approval or cause duplicate apply. Idempotent repeat of apply verifies and returns the existing matching applied result.

The transaction includes binding, current writer identity/nonces, manifest/submission/payload hashes, full before/after source manifests, snapshot paths/raw hashes, target tree hash and progress. It lives under planning, never solely `.byeori/`. Progress is a hint: recovery recomputes every file hash. For a planned file, absent is an explicit before/after state for add/delete. A current file may only match its frozen before or frozen after; unrelated source files must still match the planned full manifests. A third-party edit or unplanned path causes recovery-required with conflicts and no overwrite. Recovery can inspect without taking ownership or safely resume toward the approved after state only with verified original-death/exclusive-claim ownership. It uses frozen snapshots, never the mutable draft. After full target verification, reconstruct a missing applied record from the valid durable transaction/submission exactly once. After a valid applied record, missing cache/completion marker is housekeeping; source drift is still drift, never automatic repair.

Missing/corrupt durable recovery evidence fails closed. Cache deletion cannot discard the transaction or live ownership. No source writes can start a second transaction while an unfinished one exists. External editors can observe intermediate multi-file states, and must not be silently overwritten. B04 must inject failures at every durable/write boundary, including deletes, moves, ownership/claim publication, receipt persistence, final record persistence and cache refresh. Mandatory real-child tests pause a live writer after a file write, delete `.byeori/`, deny a second resume/managed writer and permit the original owner to continue; kill the owner and safely claim/recover; deny PID-reuse/unknown liveness and competing/partial claims; after ownership loss, resume the old invocation and assert zero further writes, including after a newer applied change. Live cache deletion and confirmed-dead crash deletion are separate cases.

## Gate, host and transport

For protected implementation writes, rederive normally completed apply, current source integrity, durable human implementation authorization, exact frozen scope, workspace identity and current policy. v0.1 uses the chain-head applied change's authorization; a newer planning-only apply cannot silently retain an older scope. Normalize every attempted path and require every one inside the frozen allowlist; directory checks use segment boundaries. Read-only investigation and managed planning-draft edits do not require implementation approval, but still use their own validated Core paths. Unknown shell/agent operations never silently pass as protected/enforced; adapter coverage explicitly identifies unsupported tools. An arbitrary shell command is not made safe by a few write regexes.

`configured`, `trusted`, `probed` and `active` are separate host observations. Active requires a successful actual native hook observation for the current version/configuration; a generated hook file, simulated probe or schema validation is insufficient. Normal gate fails closed when a required hook is inactive/unavailable. The user may explicitly select advisory mode through the human path; status/doctor/gate retain that mode and coverage limitations. Advisory affects enforcement claims only and does not waive applied/integrity/authorization/scope/policy checks. Neither development bootstrap nor environment failure automatically selects advisory. Runtime failures/timeouts on a known protected operation deny with diagnostics. Native Claude/Codex output/exit payload translation lives only in adapters.

Studio server binds 127.0.0.1 and validates Host, Origin, authenticated per-session token and mutation/CSRF context before parsing bounded input. Tokens never enter URL queries/logs/artifacts. Decode route segments once and validate; never expose arbitrary filesystem writes, SQL, shell, LLM proxy or network `$ref`. Render document/comment strings as escaped data and use a restrictive CSP; raw YAML is a supplementary view. HTTP success follows durable file success. Invalid/stale/conflict mutations map to 409 where appropriate, with safe input-preserving review guidance. Unauthenticated submission is rejected before any record writes. Accessibility, nine full-content views and user-visible stale/save/scope/permission/deletion status remain B06/B07 requirements.

## CLI, search, continuity and errors

`CLI_COMMANDS` mirrors the supplied CLI contract. `change put` supports explicit draft put/delete/move/metadata-update modes, never generic filesystem writes. Workflow save is a bounded typed operation exposed through the internal CLI change/review workflow path; it is not shell execution. Studio get/autosave/submit and advisory selection are human-only transport operations, not an agent-approval command. Queries never alter source or approval; only disposable cache freshness may be updated.

`--json` emits exactly one Result envelope on stdout; logs/progress use stderr. Diagnostics always include code/severity/path/object_id/field/message/suggested_action, with null for inapplicable location. Exit 0 succeeds, 1 unexpected, 2 validation, 3 review/scope, 4 stale/conflict/drift, 5 recovery and 6 capability. `DIAGNOSTIC_EXIT_CODES` fixes branchable error mapping. HTTP adapters preserve structured diagnostics and never return an approval-looking success after a failed save.

Search defaults to approved and limit 5, max 25. Draft change and history scopes are explicit. Rank ID exact → title/alias exact → weighted FTS → limited substring; score describes ranking, never probability. Bind SQL parameters and safely tokenize user input rather than concatenating FTS syntax. Impact returns traversed depth/count/truncation and explicitly uninvestigated code impact. History/get can address deleted before/after snapshots with their recorded revision. The index freshness key includes sorted file paths/content hashes, indexer version and scope, never Git commit alone. Detect additions/deletions/uncommitted edits, and fail closed on current source errors instead of serving a previous index as current approved. Isolate `node:sqlite`, disable extension loading, probe real FTS5 create/insert/query and support busy timeout/rebuild locking. B05 measures Korean exact/alias/FTS and agent query expansion separately; no semantic-search claim.

`ContinuityStatus` contains every supplied continuity field, using null/empty for an initial project. Workflow durably preserves focus, facts/answers, assumptions, open questions, next action, feedback progress and correction attempts with optimistic version checks. After compact/restart, start/change/review reread status + workflow + submissions/responses, verify the current round/source and continue without re-asking answered questions or repeating applied feedback. Status derives active change, current round/manifest, pending submissions, processed comments, apply state and implementation authorization from records. Approved planning, applied planning and verified implementation are different states; unverified code is never reported complete. Development `.delivery` and child/remote build state are private and unrelated to this product workflow.

## Schema normalization and B02 boundary

`schemas/planning-object.schema.json` is the provided eight-kind seed verbatim except its descriptive title; no required field or validation was removed. `schemas/review-submission.schema.json` retains all seed required fields and disallows extra properties, strengthens engine record IDs/workspace fingerprint to safe formats, adds nullable operation_id/pointer targets, makes authorization allowed/scope_hash a discriminated pair, and requires a SHA-256 expected_feedback_version plus explicit true final_confirmation. These additions permit stable OpenAPI comments, prevent contradictory scope authorization shapes and make the saved-feedback CAS precondition representable. They do not prove approval; semantic binding/saved-body equality, single-finalization, exact item coverage, target validity and stage checks remain Core responsibilities. Existing seed-shaped review input must explicitly supply the added fields, because this is the first product contract, not an installed-data migration.

The small contract test compiles both local 2020-12 schemas, validates all eight representative typed native objects and a typed mixed review/OpenAPI target, and rejects missing required content/feedback revision, unsafe record IDs and contradictory authorization. It checks that the public CLI and continuity contracts are represented. `pnpm test` uses Node's recursive tests/**/*.test.* discovery, so both tooling and contract suites (and future Node test suites) run through `pnpm check`. It is a contract representability check, not evidence of runtime human approval/recovery or full OpenAPI conformance. B04/B07 must run two-tab stale-save-submit rejection, distinct-ID finalization races, same-ID replay after restart/new round/apply, payload conflicts and finalized-autosave denial against the actual runtime.

No Core runtime implementation precedes independent B02 review. B02 should challenge source-genesis/hash derivation, frozen metadata invalidation, human-submit versus autosave, scope/workspace binding and journal recovery against third-party edits. B03/B04 implement these contracts and add their trust-boundary/fault tests. Native host capability and server/browser claims stay unverified until their separate tasks execute.
